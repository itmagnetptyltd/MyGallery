## What must be true

The five acceptance criteria, restated as the behaviour to build:

1. **A browser on the client's PC reaches a displayed Gallery** after the
   documented start steps are followed on Windows 11 with the one prerequisite
   installed.
2. **The start instructions are complete** — reaching that Gallery needs no step
   that is not written down.
3. **Exactly one prerequisite** must be installed before the application starts.
4. **Starting is one command** (or one file to open), not a sequence.
5. **The application is not reachable from another device.** A connection
   attempted from elsewhere on the network is refused.

Criterion 1 says "the Gallery is displayed". In this slice that means the
Gallery **page** loads and presents an empty Gallery region. What it *says* when
it holds no Photos is `REQ-GAL-007`, and `REQ-GAL-007` is slice 2 — this slice
must not build the no-Photos-yet message, or slice 2's tests will pass before
slice 2 is written.

## Approach

Node.js 20 or later, plain JavaScript, ESM, **no build step** — the thing you
run is the thing you wrote, which is what makes the single-command start
honest. Node is the one prerequisite; it brings `npm`, and `node:test` means the
test runner costs no dependency at all. Slice 1 adds **no runtime dependency**:
`node:http` serves the page and `node:fs` reads it. The server binds explicitly
to `127.0.0.1` rather than `0.0.0.0`, which is what satisfies criterion 5 — the
refusal is a property of the bind address, not a firewall rule the client has to
configure. Request handling is split so the parts can be tested without opening
a socket: `create-server.js` builds the handler, `server.js` is the only place
that calls `listen`. Static serving resolves the requested path and then
verifies containment inside the served directory, serving only an allow-list of
extensions with explicit content types — `rules/javascript/security.md` names a
hand-rolled static server as the most common place a plain-JS project goes
wrong, and this slice is where that code gets written.

Files created:

```
package.json              root — "type": "module", the start and test scripts
package-lock.json         root — committed, never floated
README.md                 root — the start instructions criteria 2-4 test against
src/config.js             HOST 127.0.0.1, PORT, the public directory path
src/server.js             entry point; the only caller of listen()
src/http/create-server.js request handler factory, no listen
src/http/static-files.js  path containment, extension allow-list, content types
src/http/headers.js       Content-Security-Policy, X-Content-Type-Options
src/public/index.html     the Gallery shell — heading and empty Gallery region
src/public/app.css        enough styling to look deliberate, no framework
tests/config.test.js
tests/server.test.js
tests/static-files.test.js
tests/start-instructions.test.js
e2e/boot.spec.js
playwright.config.js      root — see "What I am unsure about"
```

Every file the application is made of is under `src/`, including
`src/public/`. Nothing named `public/`, `lib/` or `app/` goes at the root.

## Test skeleton

Each test below carries `// @covers REQ-GAL-011@v1` unless marked *(hardening)*,
which means the rules require the behaviour but no slice-1 requirement names it.

**Belt A — `tests/` (`node --test`)**

`tests/config.test.js`
- `the server is configured to listen on the loopback address only`
  → asserts the configured host is `127.0.0.1`, not `0.0.0.0` and not empty.
- `the configured port is one fixed value the start instructions can name`
  → asserts the port is a number and matches the port written in `README.md`.

`tests/server.test.js`
- `a started server reports a loopback bound address`
  → `server.address().address` is `127.0.0.1`. *(criterion 5)*
- `a started server refuses a connection to the machine's network address`
  → connects to a non-loopback IPv4 from `os.networkInterfaces()` on the same
    port, asserts `ECONNREFUSED`. Skips when the machine has no such interface.
    *(criterion 5)*
- `requesting the root path serves the Gallery page`
  → 200, `content-type: text/html`, body contains the Gallery region.
- `the Gallery page is served with a content security policy` *(hardening)*
- `the Gallery page is served with nosniff` *(hardening)*

`tests/static-files.test.js` — all *(hardening)*
- `a path escaping the served directory is refused`
- `a percent-encoded path escaping the served directory is refused`
- `a dotfile is refused`
- `a file whose extension is outside the allow-list is refused`
- `a served file carries the content type for its extension`

`tests/start-instructions.test.js`
- `the start instructions name exactly one prerequisite to install`
  → parses the Prerequisites section of `README.md`, asserts one entry.
    *(criterion 3)*
- `the start instructions reach a running application in a single command`
  → asserts the start section contains exactly one command. *(criterion 4)*
- `the single start command is defined as a script in package.json`
  → the command in `README.md` is `npm start`, and `scripts.start` exists.
    *(criterion 4)*

**Belt B — `e2e/` (Playwright)**

`e2e/boot.spec.js`
- `following the documented start steps displays the Gallery in a browser`
  → Playwright starts the app with the documented command only, navigates to
    the documented address, asserts the Gallery region is visible.
    *(criteria 1 and 2)*
- `the Gallery page is reachable at the address the start instructions name`
  → the address is read from `README.md`, not hardcoded in the test, so the two
    cannot drift apart. *(criterion 1)*

Every criterion has at least one test:

| Criterion | Covered by |
|---|---|
| 1 displayed in a browser | `e2e/boot.spec.js` (both) |
| 2 instructions complete | `e2e/boot.spec.js` — proxy only, see below |
| 3 one prerequisite | `start-instructions.test.js` |
| 4 one command | `start-instructions.test.js` (two tests) |
| 5 refused from the network | `server.test.js` (two tests) |

## Decisions this forces

1. **The runtime — Node.js 20+, plain JavaScript, no build step.** This is the
   ADR I flagged at `/resolve-ambiguities`. The client said "like Python or
   Node.js", which fixed *at most one prerequisite* without choosing which.
   **Approving this plan is choosing Node**, and that choice should be written
   up with `/adr-write` rather than left implicit in a slice-1 diff.
2. **No `tsconfig.json`, ever.** The javascript adapter is selected by
   `detectUnless: ["**/tsconfig.json"]`. Adding one — even to quiet an editor —
   silently switches the project to the typescript adapter and changes every
   gate's commands and file globs. Belongs in the same ADR as a stated
   consequence.
3. **`test:integration` must exist in `package.json` from this slice.**
   `check-belt-gates.js` currently reports `integration=missing`, and six agreed
   requirements list belt C. On profile `os` that makes **G7 fail-closed
   repository-wide** — so slice 1's pull request can fail G7 even though
   `REQ-GAL-011` has no belt C. The script needs to exist and exit clean over an
   empty belt-C set now; the tests arrive in slice 2.
4. **Playwright as a dev dependency.** Belt B needs a browser driver, and a new
   dependency is a review decision under `rules/javascript/security.md`. It is
   `devDependencies` only — it changes nothing the client installs.
5. **What happens when the port is already in use.** No acceptance criterion
   covers it. I propose failing immediately with a message naming the port and
   how to change it, rather than silently picking another port the README no
   longer describes. Cheap now, and it keeps criterion 1 honest.

Deferred, not needed to close this slice: **where Photos are stored on disk**.
The client asked for "a normal folder on my disk that I can find and back up
myself" (`REQ-GAL-008`). `src/config.js` will gain that path in slice 2; it is
an ADR when it lands, not now.

## What I am unsure about

- **Criterion 2 cannot be mechanically tested.** "Followed by someone who has
  not worked on the project" is a human check. The e2e test is a proxy: it
  performs only the documented steps, so it fails if reaching the Gallery needs
  something undocumented. That is the closest a test gets. The real check is
  running the README on a clean Windows 11 machine, and I would not claim this
  criterion is verified on the proxy alone.
- **Criterion 5's second test is environment-dependent.** A machine or CI
  container with no non-loopback IPv4 interface has nothing to connect from, so
  the test skips. The bind-address assertion always runs and is the load-bearing
  one. A skipped test that looks like a pass is exactly the thing
  `rules/javascript/testing.md` warns about — flagging it rather than hiding it.
- **`playwright.config.js` at the repository root** is a deviation from the
  `src/` rule, which permits only `package.json`, the lockfile, `README.md`,
  `tests/`, `scripts/` and the toolkit directories beside `src/`. The same
  rationale as `package.json` applies — tooling reads it from the working
  directory — but it is not on the list. Alternative is `scripts/` with an
  explicit `--config` flag. **Your call.**
- **The slice-1/slice-2 boundary on the Gallery page.** I have scoped this slice
  to a page with an empty Gallery region and no empty-state message. If you would
  rather slice 1 shipped nothing visual at all and criterion 1 were proven
  against a bare 200, say so — but then "the Gallery is displayed" is not really
  what was tested.
- **80% line coverage at G2** over a slice this small is sensitive to how much
  of `server.js` is the `listen` call. If coverage comes in under, the answer is
  more of the handler moved out of the entry point, not a lowered threshold.
