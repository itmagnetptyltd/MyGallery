## Approach

Browser code and CSS only. The server, the API and the routes are untouched:
the card uses the existing `GET /api/photos/<id>/download` and
`DELETE /api/photos/<id>`.

- `src/mygallery/static/app.js` — `tileFor` appends a `div.card-actions`
  under the `.tile-frame`, holding:
  - an `<a class="outline-button" data-testid="card-download">` whose `href`
    is the Photo's download route. An anchor, not a button: the route already
    sends `Content-Disposition: attachment`, so the browser downloads with no
    script, and it is keyboard- and middle-click-friendly for free.
  - a `<button class="danger" data-testid="card-delete">`.
  Both are built with `createElement` and `textContent`, as the rest of the
  card is.
- The Gallery's delegated click handler returns early when the click lands
  inside `.card-actions`, so neither control opens the Larger view (c13, c14).
  Today the handler opens the Larger view for any click inside a card.
- Delete from a card sets the Photo the confirmation is about and opens the
  existing `deleteConfirmation` dialog. `openPhotoId` today means "the Photo
  the Larger view shows"; it becomes `pendingDeletePhotoId`, set by whichever
  control asked, so the one confirm handler serves both until slice 3 removes
  the Larger view's Delete. Confirming reloads the Gallery, which drops the
  card (c15).
- `src/mygallery/static/app.css` — `.card-actions` is a two-column grid,
  `grid-template-columns: 1fr 1fr`, which is what makes c12 true at every card
  width rather than by coincidence of label length. The buttons reuse
  `.outline-button` and `button.danger`, the look the client already chose for
  Save description and Delete. The hover lift and zoom stay on the card; the
  magnifier badge and shade stay on the image, so they never suggest that
  pressing Download opens the Larger view. `cursor: pointer` moves from the
  whole card to the image area.
