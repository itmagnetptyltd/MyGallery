## What must be true

c1-c3 are unchanged from v1 and already built and tested. They need their pins
moved, not new code.

1. **c1** A chosen file shows as a preview image before the Upload, not only
   its filename.
2. **c2** Each preview renders its own file, not another chosen file.
3. **c3** Thirty chosen files show thirty previews.

New in v2:

4. **c4 — as wide as the description box.** A chosen image at least as wide
   as the description field gets a preview exactly that wide. Today previews
   are 140-pixel-minimum tiles, several to a row.
5. **c5 — not cropped.** The preview keeps the image's width-to-height
   proportions. Today every tile is 120 pixels tall with `object-fit: cover`,
   which crops.
6. **c6 — centred when narrower.** An image narrower than the description
   field is centred horizontally in the popup, not stretched and not
   left-aligned.

## Approach

CSS only, in **`src/mygallery/static/app.css`**. `app.js` already builds one
`<li data-testid="upload-preview"><img class="upload-preview-image">` per
file, and the markup does not change.

- **`.upload-previews`** becomes a single column: `display: grid;
  grid-template-columns: 1fr`, keeping the 10-pixel gap. **Remove its
  `max-height: 320px` and `overflow-y: auto`.** The reason is under Decisions.
- **`.upload-preview-image`**: `max-width: 100%; width: auto; height: auto;
  margin-inline: auto`, keeping `display: block` and the 6-pixel radius. Drop
  `height: 120px` and `object-fit: cover`.
  - A wide image scales down to the column's width, which is the description
    field's width: both fill the popup's content box (c4).
  - `height: auto` keeps its proportions, with no crop (c5).
  - A narrow image stays its natural width and is centred by the auto margins
    (c6).
- The comment above the rule changes: it currently justifies small tiles by
  citing thirty previews.

## Decisions this forces

> **Corrected at approval, 2026-09-21 (developer).** The preview list KEEPS its
> own 320-pixel scroll box, so Upload stays in view, and hides its scrollbar
> with `scrollbar-width: none` so that previews stay exactly as wide as the
> description field (c4). The list still scrolls by wheel, touch and keyboard.
> This replaces the "popup scrolls" proposal below, which was not taken.

- **The popup scrolls, not the preview list.** Today the list has its own
  320-pixel scroll box. Keeping it breaks c4. A single full-width preview of a
  landscape photo is taller than 320 pixels, so the box grows a scrollbar,
  and the scrollbar makes the previews about 15 pixels narrower than the
  description field. Removing the inner scroll box lets the popup itself
  scroll: a native `<dialog>` already caps its height to the viewport and
  scrolls its content. The cost is that with many files chosen, the
  description field and the Upload button are below the previews, and are
  reached by scrolling the popup. The client was asked about exactly this
  trade-off. Their answer was "No, atleast a reasonable preview", which
  accepts the size and does not ask to keep Upload in view. **Correct me
  here** if you would rather keep an inner scroll box and accept previews
  slightly narrower than the field.
- No ADR needed. This is CSS only, with no new dependency.

## What I am unsure about

- **"height as per image pixel".** I read it as "height follows the image's
  proportions", because with the width fixed to the description box, a
  literal natural pixel height would stretch the image. If the client meant
  natural size, uncapped, c4 would already contradict it.
- **Small images are not enlarged.** c6 says a narrow image is centred, and I
  keep it at its natural width. No criterion asks for small images to be
  scaled up to the field's width, so this plan does not do it.
- **Thirty landscape photos at full width is a long scroll**, about 30 × 480
  pixels in a 900-pixel popup. That is what the answer asks for. It is worth
  showing the client once built.
