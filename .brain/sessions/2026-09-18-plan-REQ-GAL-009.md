## What must be true

1. An Upload interrupted before it completes leaves **no Photo** in the Gallery.
2. That same interruption leaves **no partial content** on disk.
3. Thirty files of which three cannot be uploaded leave the **twenty-seven**
   that succeeded as Photos.
4. Each of the three failed files is **named** to the user.
5. The report for a failed file shows a **reason alongside its name**.
6. A file larger than 25 MB is reported as **too large**, and the reason
   **names the 25 MB limit**.

## What is already true, and what is not

Criteria 3–6 are mostly already true **over HTTP**. Slice 2's
`POST /api/photos` keeps the good files, names the bad ones, and
`RefusalReason.TOO_LARGE.message()` is already `file is too large (max 25 MB)`
— the client's own words. Those belt-C facts stay; this slice adds `@covers
REQ-GAL-009@v1` tests rather than re-annotating `REQ-GAL-001`.

Two things are **not** true today:

- **`PhotoStore.save` is not atomic.** It writes the Photo, then the
  Thumbnail, then the index row, each to its final path. An exception after
  the first `write_bytes` leaves a file and no row — exactly the partial
  criterion 2 forbids. Criteria 1 and 2 are new work.
- **The page ignores `refused`.** `upload()` in `app.js` POSTs and reloads
  the Gallery. The twenty-seven appear; the three names and reasons never
  do. Criteria 4–6 in the browser are new work.

The client's third example — `"upload failed, please try again"` — is not an
acceptance criterion, but it is the wording they asked for when the failure
is not a type or a size. A save that throws (disk full, a write interrupted
and caught) uses that sentence. Inventing a fourth wording would be the
ambiguity this answer closed.

## Approach

**Cleanup, not a new storage shape.** `save()` writes the Photo and the
Thumbnail to sibling `*.tmp` files, `os.replace`s them into place, then
INSERTs the row. Any exception unlinks the temps and any final files this
call created, and does not leave a row. INSERT is last, so a crash cannot
publish a Photo whose bytes are not there — that is criterion 1.

A crash between `replace` and INSERT still leaves files with no row. That
is criterion 2 after a restart, so `_prepare` sweeps two things it can
recognise without guessing: every `*.tmp` in `photos/` and `thumbnails/`,
and every file in those directories whose identifier is not a row. The
inverse case — a row whose file is gone — is the stale-row problem ADR-0004
named and slice 4 deferred. This sweep does not touch it.

`upload_photos` already refuses per file and continues. It grows one
`try` around `store.save`: a thrown save becomes a `refused` entry with
`"upload failed, please try again"`, and the next file in the batch still
runs. The JSON shape does not change.

The Gallery page gains a failure list, `data-testid="upload-failures"`,
each row `data-testid="upload-failure"` carrying the filename and the
reason as `textContent`. Same rule as the tiles: never `innerHTML`. It is
not the `gallery-error` of `REQ-GAL-007` — that is an unreadable Gallery;
this is an Upload that said what it could not take. Hidden when `refused`
is empty, including after a later Upload that refused nothing.

Files:

```
src/mygallery/photos/store.py              save() writes via *.tmp;
                                           _prepare sweeps leftovers
src/mygallery/web/api.py                   catch save errors per file
src/mygallery/templates/gallery.html       + upload-failures list
src/mygallery/static/app.js                render body.refused
src/mygallery/static/app.css               the list
tests/test_upload_failures.py              A
tests/api/test_upload_failures_http.py     C
tests/e2e/test_upload_failures_browser.py  B
```

`validation.py` is left alone. Criterion 6 is already the message it
returns; the new tests pin that it is *shown*.

## Test skeleton

Annotation `# @covers REQ-GAL-009@v1`.

**Belt A — `tests/test_upload_failures.py`** (the store, in isolation)

Make `save` fail after the Photo bytes have been written — monkeypatch the
Thumbnail write, or the second `replace`. Then:

- `an_interrupted_save_adds_no_photo` *(1)* — `store.all()` is empty
- `an_interrupted_save_leaves_no_photo_file` *(2)* — `photos/` has no file
  whose bytes came from the Upload
- `an_interrupted_save_leaves_no_thumbnail` *(2)* — `thumbnails/` is empty
- `an_interrupted_save_leaves_no_temp_file` *(2)* — no `*.tmp` either
- `opening_the_store_removes_a_file_that_has_no_row` *(2)* — plant an
  orphan, call `PhotoStore.open()`, it is gone
- `the_too_large_reason_names_the_25_mb_limit` *(6)* —
  `RefusalReason.TOO_LARGE.message()` is `file is too large (max 25 MB)`

**Belt C — `tests/api/test_upload_failures_http.py`**

- `uploading_thirty_of_which_three_fail_keeps_twenty_seven` *(3)*
- `each_failed_file_is_named_in_the_response` *(4)* — the three filenames
- `each_failed_file_carries_its_reason` *(5)* — reason sits on the same
  object as the name
- `an_oversized_file_is_reported_as_too_large_with_the_limit` *(6)* —
  reason contains `too large` and `25 MB`
- `a_save_that_throws_is_reported_and_leaves_no_photo` *(1, 2)* —
  monkeypatch `PhotoStore.save` (or the write) to raise after creating a
  file; the body names the file, the Gallery listing is empty, the
  directory holds nothing from it
- `a_save_that_throws_in_a_batch_does_not_stop_the_others` *(3)* — one
  throwing file among good ones; the good ones are Photos

**Belt B — `tests/e2e/test_upload_failures_browser.py`**

No `wait_for_function`. `expect(...)` on the list and the count.

- `a_batch_with_three_failures_keeps_the_photos_that_worked` *(3)* —
  twenty-seven Thumbnails (or `photo-count` is `27`)
- `each_failed_file_is_named_on_the_page` *(4)*
- `each_failure_shows_its_reason_beside_its_name` *(5)*
- `an_oversized_file_names_the_25_mb_limit_on_the_page` *(6)* — pad a
  JPEG past `MAX_PHOTO_BYTES` on disk; the shown reason contains `25 MB`

## Decisions this forces

**None that warrant an ADR.** Temp-then-replace and the leftover sweep are
the only honest reading of criteria 1 and 2 against ADR-0004's three
locations. Changing the sweep later is an edit to `_prepare`, not a
migration. The failure list's placement is trivially reversible.

## What I am unsure about

- **"Interrupted" is not a user action the requirement describes.** I am
  treating it as *any `save` that does not return* — an exception, or a
  crash reconstructed by leftovers on the next `open()`. If the client
  meant the browser cancelling a request mid-body, Flask will not have
  called `save` yet and there is nothing to clean. The tests say which
  reading was used.
- **The orphan sweep is the inverse of the stale-row problem, and I am
  doing only this side.** A file with no row is leftover write; a row with
  no file is the Explorer-delete case slice 4 deferred. Sweeping both on
  `open()` would silently drop rows the client might still want explained.
  I will not take that decision here.
- **Thirty files in the browser is slow but cheap.** Slice 2's belt B used
  three for the happy batch. Criterion 3 says thirty, so belt B will too.
  Say if you want the count asserted on a smaller mixed batch and the
  thirty left to belt C.
- **A 25 MB+ fixture in Playwright will be felt.** The file is padded
  zeros on a real JPEG, written once per test, not committed. If that is
  too heavy for the suite, criterion 6 in the browser can be dropped and
  left to A and C — that is a judgement I will not make for you.
- **The Download control from slice 5 is still missing.** Out of this
  slice. Not touching `download-photo`.
